## 1. 项目背景与目标

### 1.1 业务背景

WaytoAGI 是一个聚焦 AGI（通用人工智能）领域的社区，目前在东莞已有稳定的线下活动节奏（meetup、分享会、闭门讨论等）。当前痛点：

- **报名分散**：使用问卷星、腾讯文档、金数据等工具报名，数据散落、统计繁琐。
- **缺乏品牌统一性**：报名页样式各异，无法形成 WaytoAGI 东莞的对外品牌。
- **签到依赖人工**：现场靠微信群核对名单，效率低、易漏、易重复。
- **数据未沉淀**：报名数据难以二次分析（到场率、地域分布、职业画像）。
- **多区域扩展**：后续计划在广深、上海、北京等城市拓展，需要一套可复用的平台底座。

### 1.2 项目目标

| 时间维度 | 目标 |
| --- | --- |
| **首期（M0 → M3）** | 上线 MVP，跑通东莞首场线下 meetup 全流程（发布→报名→通知→签到→数据沉淀） |
| **中期（M3 → M6）** | 支持多活动并发运营、提供主办方自助数据看板、沉淀活动模板 |
| **长期（M6+）** | 多区域（多 region）能力开放、支持赛事/邀请制等复杂场景、可对外赋能其他城市运营 |

### 1.3 名词定义

| 名词 | 含义 |
| --- | --- |
| **参与者** | 浏览/报名/签到活动的用户（含未登录游客与已登录用户） |
| **主办方** | 拥有「组织」账号、能创建与管理活动的运营方 |
| **组织** | 主办方归属的运营主体（两级结构：组织 → 成员） |
| **运营** | 平台超级管理员，拥有跨组织审计与干预能力 |
| **志愿者** | 协助现场签到的角色（与主办方身份合一，无独立账号体系） |
| **活动** | 一次具体的线下聚会 / 赛事 / 邀请制活动 |
| **场次 / 期次** | 同一活动下的多个时间段（一期/二期/上午场/下午场） |
| **活动模板** | 平台预置或主办方保存的活动配置（表单字段 + 通知模板） |
| **Region** | 区域字段，预留后续多城市扩展 |

## 2. 目标用户与场景

### 2.1 用户画像

| 角色 | 典型画像 | 核心诉求 |
| --- | --- | --- |
| **参与者** | 东莞 AGI 兴趣者、开发者、产品经理、学生 | 报名顺畅、提醒及时、现场签到快 |
| **主办方** | WaytoAGI 东莞志愿者团队负责人 | 一站式创建活动、收集名单、现场签到、数据复盘 |
| **运营** | 平台超级管理员（项目团队内部） | 全局活动审核、组织管理、平台数据看板 |
| **志愿者** | 主办方成员兼任 | 现场扫码签到、补报名、状态查询 |

### 2.2 关键场景（首场东莞 meetup 锚点）

**场景 A：发布活动**
WaytoAGI 东莞组织者「林一」登录后台 → 选择「东莞周会·主题：RAG 实战」模板 → 填写时间地点与表单 → 上传封面图到 OBS → 一键发布上线。

**场景 B：用户报名**
用户「小张」在公众号文末看到链接 → 微信扫码登录 → 填写报名表（姓名/手机/公司/职位）→ 收到报名成功通知 + 活动电子票邮件 → 活动前一天收到短信提醒。

**场景 C：现场签到**
活动当天，小张到达现场后打开电子票页出示二维码 → 志愿者老王用工作端扫码 → 系统自动标记签到成功并推送欢迎语；如二维码无法识别，老王手动输入手机后 4 位检索完成签到。

**场景 D：活动复盘**
活动结束后，主办方在后台导出签到名单 Excel、上传活动复盘文 → 通过站内信 + 公众号文触达所有报名用户。

## 3. MVP 范围与优先级（MoSCoW）

### 3.1 Must Have（首场东莞 meetup 必需）

- 微信扫码登录 + 手机号+验证码登录
- 主办方两级组织管理（组织 → 成员）
- 活动 CRUD：创建 / 编辑 / 上架 / 下架 / 复制
- 平台预置 3 套活动模板（meetup / 赛事 / 邀请制）
- 在线报名 + 自定义表单字段（文本/单选/多选/手机/邮箱）
- 名额控制 + 场次/期次选择
- 三种签到方式：自报二维码 / 组织者扫微信群二维码 / 手机后 4 位搜索
- 通知：微信服务通知 + 邮件（电子票） + 短信（活动前一天提醒）
- 报名名单 + 签到记录导出（Excel/CSV）
- region 字段（首期固定为「东莞」）

### 3.2 Should Have（首月内补齐）

- 站内信 + 公众号文推送
- 多活动汇总报表（数据看板）
- 主办方私有活动模板保存
- 活动审核流（运营可下架问题活动）
- 现场补报名（快速录入）

### 3.3 Could Have（下个迭代）

- 邀请码 / 白名单（邀请制活动强化）
- 队伍报名（一对多组队）
- API / 开放接口供主办方拉数据
- 平台公开模板市场

### 3.4 Won't Have（明确不做）

- 在线支付（首期全部免费活动）
- 多语言 i18n
- 直播 / 录播功能
- 复杂的多级组织树（先两级）

## 4. 业务模型与权限设计

### 4.1 核心实体关系（ER 概览）

```
User（账号）
  ├─ 1:N → OrganizationMember（组织成员关系）
  │           └─ N:1 → Organization（组织）
  │                     └─ 1:N → Activity（活动）
  │                                 ├─ 1:N → ActivitySession（场次/期次）
  │                                 ├─ 1:N → FormField（自定义表单字段）
  │                                 ├─ 1:N → Registration（报名）
  │                                 │         └─ 1:1 → Ticket（电子票）
  │                                 │                   └─ 1:1 → Checkin（签到）
  │                                 └─ 0:N → Notification（通知记录）
  └─ 1:N → Region（多区域扩展位）
```

### 4.2 角色与权限矩阵（身份合一原则）

> **设计原则**：账号、组织、活动三个维度解耦；一个账号可在不同组织担任不同角色，在同一活动内可同时是「主办方成员」+「报名参与者」。

| 能力 | 游客 | 注册用户 | 主办方成员 | 组织 Owner | 平台运营 |
| --- | :---: | :---: | :---: | :---: | :---: |
| 浏览活动详情 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 报名活动 | ❌ | ✅ | ✅ | ✅ | ✅ |
| 创建活动 | ❌ | ❌ | ✅ | ✅ | ✅ |
| 编辑/下架活动 | ❌ | ❌ | 自己创建的 | 组织内全部 | 全部 |
| 管理组织成员 | ❌ | ❌ | ❌ | ✅ | ✅ |
| 现场签到 | ❌ | ❌ | ✅ | ✅ | ✅ |
| 导出本组织数据 | ❌ | ❌ | 部分 | ✅ | ✅ |
| 跨组织审计 | ❌ | ❌ | ❌ | ❌ | ✅ |
| 平台配置 / 模板维护 | ❌ | ❌ | ❌ | ❌ | ✅ |

### 4.3 区域（region）扩展策略

- 所有活动、用户、报名记录均带 `region_code` 字段（首期默认 `DG` 东莞）。
- 后续新增 region 仅需配置 region 字典 + 部署子域名，无需改业务逻辑。
- 运营管理后台支持按 region 过滤。
- **首期仅部署东莞 region**，其他 region 在 UI 灰度开放。

## 5. 功能详细说明

### 5.1 账号与认证

| 能力 | 说明 |
| --- | --- |
| 微信扫码登录 | 微信开放平台 → 网站应用扫码登录；首次登录自动注册 |
| 手机号+验证码 | 腾讯云短信发送 6 位验证码，5 分钟内有效 |
| 账号合并 | 同一用户先用手机号注册后绑定微信 → 自动合并 |
| 游客报名 | 必须登录后才能报名（保证后续通知可触达） |

### 5.2 组织管理（两级组织树）

- **组织创建**：任意已登录用户可创建组织，自动成为 Owner。
- **成员邀请**：通过微信扫码 / 邀请链接加入组织；Owner 可设置成员角色（管理员 / 普通成员）。
- **组织信息**：组织名、Logo、简介、region、联系方式。
- **首期组织样例**：`WaytoAGI 东莞`（顶级组织）→ 内部分若干小组/活动负责人。

### 5.3 活动管理

- **创建活动** 流程：
  1. 选择模板（Meetup / 赛事 / 邀请制） 或 从历史活动复制
  2. 填写基本信息（标题、封面、简介、时间地点）
  3. 配置场次（可多期次）
  4. 拖拽配置自定义表单字段
  5. 配置通知模板（报名成功 / 活动提醒 / 签到成功 / 活动结束）
  6. 预览 → 提交 → 审核（首期仅运营可审核）→ 上架
- **活动状态机**：`草稿 → 审核中 → 已上架 → 进行中 → 已结束 → 已下架`
- **活动下架**：主办方自行下架 / 运营强制下架（需记录原因）
- **活动模板**：平台预置 3 套（meetup/赛事/邀请制），主办方复制后自定义。

### 5.4 报名管理

- **报名字段类型**：单行文本、多行文本、单选、多选、手机号、邮箱、日期。
- **名额控制**：
  - 总名额 + 每场次名额
  - 报名时间窗口（开始时间 / 截止时间）
  - 满员后支持候补队列
- **报名状态机**：`待审核 / 已通过 / 已拒绝 / 已签到 / 已取消`
- **邀请制活动**：仅白名单内用户可报名（白名单导入或邀请码）。

### 5.5 签到核销

| 方式 | 实现 | 适用场景 |
| --- | --- | --- |
| **自报二维码** | 报名成功后生成唯一 Ticket QR，志愿者扫码端调用 `POST /checkin/scan` | 主流方式，快 |
| **组织者扫微信群二维码** | 扫到陌生 QR 自动查询报名库匹配（兜底） | 极端情况 |
| **手动搜索手机后 4 位** | 输入框 + 实时搜索 | 二维码失败兜底 |
| **现场补报名** | Should Have 阶段，扫码或手动录入 |

签到记录字段：签到时间、签到方式、签到人（志愿者）、定位（可选）。

### 5.6 通知提醒

| 触发时机 | 渠道 | 内容 |
| --- | --- | --- |
| 报名成功 | 微信服务通知 + 邮件 | 报名确认 + 电子票 |
| 报名审核通过 | 微信服务通知 + 站内信 | 审核结果 |
| 活动前 24 小时 | 短信 + 微信服务通知 | 活动提醒（含地址定位） |
| 签到成功 | 微信服务通知 | 欢迎语 + 现场指引 |
| 活动结束 | 站内信 + 公众号文 | 复盘文 + 资料下载 |

通知模板支持变量插值（`{{user_name}}` `{{activity_title}}` `{{start_time}}` 等）。

### 5.7 数据导出

- **报名名单导出**：Excel/CSV，字段含报名时间、姓名、手机、微信、公司、职位、场次、状态。
- **签到记录导出**：签到时间、方式、志愿者、定位。
- **多活动汇总报表**（Should Have）：平台运营视角，按组织/region/时间维度聚合。

### 5.8 平台运营

- 活动审核列表（按 region 过滤）
- 强制下架 / 投诉处理
- 平台数据看板（用户数、活动数、报名数、签到率）
- 活动模板维护（增/改/下架）

## 6. 非功能性需求

### 6.1 性能

- 首场目标：单活动 200 人，瞬时报名并发 50。
- 报名接口 P95 < 500ms，签到扫码 P95 < 300ms。
- 静态资源走 CDN + OBS，前端首屏 < 2s。

### 6.2 安全与合规

- 个人信息加密存储（手机号、身份证等敏感字段 AES）。
- HTTPS 全站，HSTS 启用。
- 微信 access_token / 短信模板 ID 等密钥托管在密钥管理服务（首期可用环境变量）。
- 报名接口限流（IP + 账号维度）。
- 隐私政策页面：明示数据收集范围与用途。

### 6.3 可观测性

- 后端结构化日志（JSON）→ 集中收集（首期可写文件 + Loki/ELK 预留）。
- 关键指标埋点：报名转化率、签到率、接口成功率。
- 错误告警：5xx 错误率 > 1% 触发告警。

### 6.4 可扩展性

- 所有业务实体带 `region_code`。
- 通知渠道抽象为 `NotificationChannel` 接口，新增渠道不需改业务代码。
- 活动模板机制允许后续接入模板市场。

## 7. 技术选型与架构

### 7.1 总体架构

```
┌──────────────────────────────────────────────────────┐
│                      前端 (Web)                       │
│  React + TS + Vite + Tailwind + shadcn/ui + zustand  │
└──────────────────┬───────────────────────────────────┘
                   │ HTTPS / JSON
┌──────────────────▼───────────────────────────────────┐
│                  后端 API (NestJS)                    │
│  Modules: auth | org | activity | registration       │
│           checkin | notification | admin              │
└──┬──────────────┬──────────────┬─────────────────────┘
   │              │              │
   ▼              ▼              ▼
┌──────┐    ┌──────────┐   ┌──────────┐
│ PG   │    │   OBS    │   │  Redis   │
│(主存)│    │(对象存储) │   │ (缓存)   │
└──────┘    └──────────┘   └──────────┘
                ▲
                │ 静态资源 / 报名附件
                │
        ┌───────┴────────┐
        │  微信开放平台   │
        │  短信 / 邮件   │
        └────────────────┘
```

### 7.2 技术栈

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 前端 | React 18 + TypeScript + Vite + Tailwind + shadcn/ui + zustand + axios | 团队熟悉、组件库齐、社区活跃 |
| 后端 | Node.js + NestJS + TypeScript + Prisma | 类型一致、生态成熟、模块化清晰 |
| 数据库 | PostgreSQL 16 | 关系型强、JSON 支持好、扩展稳定 |
| 缓存 | Redis 7 | 限流、会话、热点缓存 |
| 对象存储 | OBS（华为云对象存储） | 用户指定，覆盖静态资源/附件 |
| 消息 | 微信订阅消息 / 腾讯云短信 / SMTP 邮件 | 首期选型清晰 |
| 部署 | 应用部署待定（候选：Docker 镜像 + 轻量云） | TBD |
| CI | GitHub Actions | 与代码仓库同平台 |

### 7.3 部署形态

- **静态资源**：前端构建产物 + 用户上传文件 → OBS + CDN。
- **后端**：Docker 镜像，首期可部署在 1 台 2C4G 云主机。
- **数据库**：托管 PostgreSQL（首期可用自建 + 定期备份）。
- **密钥管理**：环境变量 + 密钥文件（首期简化）。

### 7.4 第三方依赖

- 微信开放平台（网站应用）→ 扫码登录 + 订阅消息
- 短信服务（腾讯云/阿里云） → 验证码 + 提醒
- 邮件服务（SMTP / SendGrid 替代）→ 电子票

## 9. 团队分工与 Git 协作

### 9.1 角色矩阵

| 成员 | 主职责 | 次职责 | 评审范围 |
| --- | --- | --- | --- |
| **幻想** | 前端架构 + 核心组件 + 业务页面 | UI/UX 走查、移动端适配 | 前端 PR |
| **知了** | 后端核心模块（auth / org / activity） | 数据库设计、API 文档 | 后端 PR |
| **杰** | 后端支撑模块（registration / checkin / notification） | 第三方对接、运维脚本 | 后端 PR |
| **北葵** | 产品检测（QA / 质量验收） | 验收用例设计、UAT 主导、Bug 跟踪 | 全部 PR（侧重功能与体验） |

### 9.2 Git 协作规范

- **分支策略**：
  - `main` — 受保护，仅通过 PR 合并
  - `develop` — 集成分支，每日合并 feature
  - `feature/*` — 功能分支（如 `feature/frontend-registration-form`）
  - `fix/*` — 缺陷修复
  - `release/*` — 发布准备
- **PR 流程**：
  1. 从 `develop` 切出 `feature/*`
  2. 提交时遵循 Conventional Commits（`feat:` `fix:` `docs:` `refactor:` `test:` `chore:`）
  3. PR 需关联 Issue / 描述「实现思路 + 测试方法 + 影响范围」
  4. 至少 1 人 Review 通过（北葵全程 Review 关键 PR）
  5. 通过 CI 后 Squash 合并
- **Worktree 推荐**：每个功能分支使用独立 worktree，避免冲突。

### 9.3 沟通节奏

- **每日站会**（15 分钟）：昨日完成 / 今日计划 / 阻塞项
- **周会**（1 小时）：里程碑回顾 + 下周计划
- **PR Review SLA**：工作日 4 小时内首次响应，24 小时内 Review 完成
- **Bug 等级**：P0（线上故障，1h 内响应） / P1（功能阻塞，4h） / P2（一般，1 工作日） / P3（建议，1 周）
